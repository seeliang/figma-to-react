# Implementation Plan: Workspace foundation — one install, a real graph, three published 0.1.0s

**Branch**: `001-nx-pnpm-workspace` | **Date**: 2026-09-05 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `/specs/001-nx-pnpm-workspace/spec.md`

## Summary

Establish an Nx + pnpm workspace holding three near-empty packages, publish all three at `0.1.0` to
GitHub Packages from a GitHub Actions pipeline, and prove the release path end to end while the
payload is still empty.

The technical approach is **native configuration orchestrated by Nx, not replaced by it**: each
package declares plain `scripts` (`tsc -b`, `vitest run`, `prettier --check`), TypeScript project
references express the same edge the manifests do, and Nx supplies only what pnpm alone cannot —
task graph, caching, affected detection and chained versioning. No Nx executor wraps a compiler, so
every tool remains swappable in one line (constitution **P1**).

Three findings shape the rest. **This project shares `seeliang/figma-to-react` with an unrelated
lineage** (R0) — deliberately — so FR-031's "the default branch" means **`release`**, not GitHub's
default of `main`; CI triggers and the affected base both target `release`. **GitHub Packages
requires authentication to install even public packages** (R1, verified with a live 401), which
makes credential setup a first-class part of the contributor's first five minutes rather than a
footnote. And from the Constitution Check rather than from research: **P4 asserted something
untrue**, corrected in constitution 4.0.0 rather than worked around.

## Technical Context

**Language/Version**: TypeScript 7.0.2 (the Go-native compiler; `latest`, 5.x line finished),
targeting ES2022 / NodeNext

**Primary Dependencies**: Nx 23.2.0 (orchestration, caching, affected, release), pnpm 11.25.0
(workspaces, `workspace:` protocol, publish-time rewriting), Vitest 5.0.0, Prettier 3.x. No ESLint —
see R6.

**Storage**: N/A. The only persisted state is the pnpm lockfile and the Nx local task cache, both
excluded from version control except the lockfile.

**Testing**: Vitest 5, one root config, `test` script per package. Plus two repository-level check
scripts: `verify-no-workspace-refs.mjs` (FR-027) and the cycle-detection test (FR-014, R8).

**Target Platform**: Node **≥26** declared in `engines`; CI on Node 26. Contributors on macOS or
Linux; pipeline on Linux. Node 26 is *Current*, not yet LTS — it enters LTS in late October 2026
(see R5).

**Project Type**: Monorepo workspace — a published library set plus repository tooling. Three
projects at completion: `ai-plugin/core`, `ai-plugin/cli`, `packages/theme`.

**Performance Goals**: A no-change repeat of full verification under 10% of the first run's duration
(SC-003). Clone to green build under 15 minutes including credential setup (SC-001).

**Constraints**: Publishing only from the pipeline (FR-030). No credential in the repository
(FR-034). No long-lived secret where a run-scoped identity suffices (FR-033). Nothing authored under
`packages/*/src/` (**P4**, as corrected in 4.0.0); boundary files beside it are authored.

**Scale/Scope**: 3 projects, 1 internal edge, 1 external edge, 2 workflows, ~2 check scripts. Every
package is deliberately near-empty; content is later features.

**Gate result: PASS.** No unjustified violations. One entry in Complexity Tracking, structural
rather than discretionary.

**Post-Phase-1 re-evaluation**: unchanged. The design artifacts introduced no new dependency, no
wrapper over native configuration, and no authored source under `packages/*/src/`. The two check
scripts in `scripts/` are repository tooling, which **P2** places outside `packages/` — where they
are.

### What the gate actually caught

Worth recording, because a gate that never fails is decoration. It caught three things, and one of
them was a defect in the constitution itself.

- **P4 was wrong, and the gate is how it was found.** *"Nothing under `packages/` is authored"*
  cannot hold: a package needs a manifest, and no generator can write one for a package that does
  not yet exist. Corrected in **constitution 4.0.0** — the prohibition reads on `packages/*/src/`,
  boundary files are named as authored. Amending the law was the right move here rather than
  routing around it, because the rule as written would have blocked every future package too, not
  just this one.
- **FR-039** asserted all three packages define four task kinds. Split into FR-039a (the two
  `ai-plugin` packages) and **FR-039b** (`theme` is manifest-only). This one survives the
  constitution fix on its own merits: theme's content is generated, and hand-writing a placeholder
  entry point creates precisely the file the first generation run deletes (**P3**). It also makes
  `theme` the repository's live case for FR-009 and FR-017.
- **FR-044** asserted the published theme package "imports without error". A manifest-only package
  has no entry point. Amended to installs-and-resolves; SC-010 follows.

```text
├── tsconfig.json
├── src/index.ts
└── test/

    └── cycle-detection.test.ts     # mutate + restore from git index — FR-014, R8

├── package.json                    #   a boundary file — authored, beside src/ — P4
└── README.md
```

**Structure Decision.** Two workspace locations, exactly as constitution **P4** names them:
consumer-installable code in `packages/`, generator and repository tooling in `ai-plugin/`. The one
internal edge runs `ai-plugin/cli` → `ai-plugin/core`, which is a real direction (a command-line
entry point over a library) and not one invented to satisfy FR-012.

`packages/theme` is disconnected on purpose and stays that way: the generator writes the design
system, it does not consume it, so wiring `ai-plugin/*` to `theme` would manufacture an edge that
contradicts **P6**. That disconnection is not a wart — it is what makes FR-017 testable, and
`theme`'s absence of tasks is what makes FR-009 testable.

Repository-level check scripts live in `scripts/` rather than inside a package, because they are
about the workspace rather than about any project in it.

## Risks

| Risk | Impact | Mitigation |
| ---- | ------ | ---------- |
| CI or `affected` wired to `main` instead of `release` | `main` is the other lineage — PR checks never fire, and `affected` compares against unrelated history | R0 names `release` as this project's integration branch. Every workflow trigger and every `--base` uses it. |
| `gh` token lacks the `workflow` scope | A push containing `.github/workflows/*` is rejected | `gh auth refresh -s workflow` before the workflow task. Noted in R0. |
| Node 26 is *Current*, not LTS until late Oct 2026 | Runtime surprises on a line with a shorter support record | Deliberate; LTS is ~7 weeks out and the codebase is near-empty. Published `engines` should be relaxed separately once these packages have runtime behaviour (R5). |
| TypeScript 7 is two months old and this is a `tsc -b` project-references build | Build breaks in a way unfamiliar to everyone | Nothing wraps the compiler, so the fallback to 5.9 is one line in one place. Three near-empty packages is the cheapest moment to discover it. |
| Cross-repo read of the sample package needs a settings grant, not code | CI install fails with a 401 that looks like a credential bug | Explicit prerequisite task alongside R0: Manage Actions access → Add Repository. Documented in the contract so the next person does not rediscover it. |
| `projectsRelationship` left at the `fixed` default | **SC-008 passes while proving nothing** — the worst failure mode here, because it is green | Called out in R2 as load-bearing; `quickstart.md` verifies the *reason* `cli` bumped, not merely that it did. |
| nrwl/nx#27823 — dependents over-bumped under independent versioning | Wrong version numbers at release | Cannot bite with one dependency and one dependent. Recorded for the second edge. |
| Provenance is weaker on GitHub Packages than on npm | FR-037 satisfied in letter, thinner in practice | Limit recorded in R3 rather than glossed; revisit if the registry ever changes. |
